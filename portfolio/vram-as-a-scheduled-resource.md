# VRAM as a Scheduled Resource

## The cliff

The machine this whole project lives on is a laptop with an RTX 3060 and 6 GB of VRAM. That is the entire budget: no second card, no upgrade path, no cloud fallback that wouldn't defeat the point of running models locally. A 6 GB card is enough to run one quantized model well — a Gemma-class 4B at Q4_K_M is about 4 GB offloaded — and it is exactly one model, because nothing about the standard serving stack is designed to share.

The failure mode I set out to eliminate is the one every local-inference user knows. You start a server with a chat model. It loads, occupies most of the card, works fine. Then you want embeddings for a RAG pipeline, and the embedding model either doesn't fit or displaces the chat model, depending on how the server handles loads. You want an OCR model for document ingestion, and now you're choosing which capability to sacrifice. Worse, the failure is often not a clean refusal — it's an OOM partway through a decode, a context allocation that succeeded at startup and blows up when the KV cache grows, or a slot that gets corrupted by a failed speculative decode and poisons the next request on it. Small-GPU local inference isn't underpowered so much as it is a cliff: everything works until one byte over, and then nothing does.

The premise behind mettle is that this is a scheduling problem, not a hardware problem. A 6 GB card genuinely can host a chat generator, an embedding model, and an OCR vision model at the same time — a chat model at 128K context measured 4.3 GB of the 6.0 available on this card — but only if something treats VRAM the way an OS treats physical memory: as a resource with admission control, measured footprints, and a defined behavior when a request doesn't fit. mettle is a single Rust daemon (`mettled`) around an embedded llama.cpp core — the `llama-cpp-2` bindings — that serves OpenAI-, Ollama-, Anthropic-, and Cohere-shaped APIs from one port, and whose real product is the thing none of those APIs specify: a profile manager that loads and unloads models by alias against a fixed VRAM budget, degrading in defined steps instead of crashing.

## The first engine was the wrong engine, and the numbers said so

mettle didn't start on llama.cpp. It started on mistralrs, a pure-Rust inference stack, which was the reasonable choice: one dependency, OpenAI routes included, and no C++ toolchain in the build. The vendored fork lived in the repo, and the early work was making it fit the card at all.

It didn't, really. Gemma's per-layer-embedding table alone wanted ~5.25 GiB in F16 on the GPU before a single decoder layer was mapped, so an 8 GB card was nearly full before inference started. I verified by source inspection that the paged KV allocator was sized for all 42 layers of the E4B even though the architecture computes KV for only 24 — the top 18 layers are shared and never write their own cache, but the allocator didn't know that, so roughly 43% of the KV pool was dead VRAM. I had a patch target picked out and everything. The fork's PLE-on-CPU fix got the E4B onto the 6 GB card at ~5 GB, which sounds like success until you read the decode rate: 8–10 tokens/second at about 19% GPU utilization, versus Ollama's ~24.5 on the same hardware. The model fit and the engine was the bottleneck — candle's CPU quant kernels losing to llama.cpp's, plus the over-allocated KV, plus CPU-resident layers serializing the whole thing.

This is the part of the story I'd have gotten wrong without a gate clause in the spec. The spec said the engine decision reopens if throughput misses the bar, and it did — by 2.4×. The correct response was not to patch mistralrs harder. It was to run a throwaway spike crate against `llama-cpp-2`, load the same E4B GGUF with all 43 layers offloaded, and measure: ~71 tok/s at 97% GPU utilization, ~4.0 GB VRAM, 1.87 s load. Roughly 7–9× over what we had, 3× over Ollama. That single afternoon of numbers ended the mistralrs era and deleted an entire fork, a `[patch.crates-io]`, and a planned upstream patch I'd spent real time verifying. The lesson generalizes: when a foundation is wrong, measure the replacement before mourning the sunk cost.

The migration itself was a phase plan I executed over subsequent weeks, and it went the way these things actually go — the part everyone fears (writing your own continuous-batching scheduler, because llama.cpp gives you `llama_decode` and a batch, not a server) turned out to be tractable precisely because the bindings are thin, and the parts nobody warns you about were where the time went. llama.cpp gives you no HTTP server, no scheduler, and no API surface; what it gives you instead is correctness at the kernel layer, cross-layer KV sharing and PLE placement handled natively, and a `!Send` `LlamaBackend` that can only ever be initialized once per process. That last constraint shaped the whole architecture: one worker thread owns the backend and every loaded model, a bridge thread forwards requests off the tokio channel the routes use, and "slots, not processes" isn't a philosophy — it's a consequence of the FFI boundary. You cannot spawn a second engine. Models are slots loaded and unloaded by alias inside the one worker, atomically, because that's the only topology the binding permits. The tradeoff is honest and documented in the code: a model load blocks all generation briefly, not just the loading slot, and activation is therefore a first-class visible state rather than something hidden under latency.

The FFI layer had teeth beyond that. Gemma's chat template makes llama.cpp's C `llama_chat_apply_template` return -1 — it only matches a few built-in templates, not full jinja — so mettle renders prompts itself, splicing special-token IDs (105/106, stable across Gemma generations) directly because the tokenizer maps the marker strings to seven literal text tokens instead of the specials, producing malformed prompts and garbage output that took real debugging to attribute. The `LlamaContext<'static>` needed a documented transmute with model fields declared after context fields so they drop last. None of this is interesting design; all of it is the cost of owning the boundary instead of renting it from a sidecar process. The alternative — spawning `llama-server` and proxying, which is literally how Ollama works — would have bought the scheduler and routes for free, and was kept as a documented fallback. It violated the spec's single-process requirement, and by the end it was clear the single process was the feature: profiles can unload and load models atomically precisely because nothing is a separate process with its own CUDA context.

## The degradation ladder

The centerpiece is the profile manager, and the design question behind it is deceptively simple: when a requested model set doesn't fit, what should happen?

The naive answers are all bad. Load everything and OOM at the CUDA allocator — the cliff. Refuse anything that doesn't fully fit — a 6 GB card that runs three models at reduced capability gets replaced by a card that runs one. Silently pick something — unreproducible behavior that no downstream consumer can plan around. The design that finally went in is a ladder, declared per slot, walked in priority order.

A profile is a named, ordered set of slots. Each slot references a catalog model with a role — `chat`, `embed`, `rerank`, `ocr` — an optional priority, and an optional `min_ctx`. One profile is active at a time. Activation is a diff against current residency: models that stay resident between profiles are never touched, the diff's removals unload first, then loads proceed by priority. Nothing about this is exotic; what makes it work is that every step has a defined failure behavior.

Before loading anything, the planner computes each slot's cost from the GGUF header: exact weights bytes, exact KV bytes per token from the attention geometry, and a compute-buffer heuristic. Budget is device free memory minus a configured safety margin. If the full context fits, load it. If not, and the slot opted in with a `min_ctx`, shrink the context — halving KV per step — and retry, down to the floor. If even the floor doesn't fit, drop the slot. Load-time OOM from `cudaMalloc` is not an exception path; it's a rung on the same ladder, caught, emitted as an event, and the activation continues downward. If even the highest-priority slot can't load, the activation is refused outright, current state is preserved, and the shortfall is reported. The invariant the whole thing hangs on: nothing degrades silently. Every shrink and every drop emits a `profile.degraded` event naming exactly what changed and why, and a request to a dropped slot gets a structured 503 with `slot_unavailable` and a `Retry-After` — not a generic error a client has to guess at.

Concretely, on this machine: the retrieval profile holds the embedding model (445 MB measured) and a reranker (325 MB measured) with the chat generator's slot at full context. Switch to the chat-heavy profile and the ladder has room to keep the embedder resident at shrunk context while the chat model takes its 4.3 GB. Ask for a profile whose chat model is a 26B MoE and the ladder walks: full doesn't fit, shrink toward `min_ctx`, still doesn't fit, drop the OCR slot, retry, and if the first slot itself can't place, refuse and keep serving what was already there. Each of those outcomes is observable on an SSE event bus that replays the last 100 events on connect, because a scheduler you can't watch is a scheduler you can't trust.

Two design decisions inside the ladder are worth defending. First, degradation never falls back to CPU. A slot can be *pinned* to CPU by explicit config intent — that's how the retrieval coexistence used to happen implicitly — but the ladder's failure mode is dropping the slot, not silently moving it to system RAM, because a model that answers in 2 tok/s is not a degraded version of the service, it's a different and worse service the user didn't ask for. Second, model switching supersedes rather than queues: a second activation arriving mid-switch recomputes the diff from current state and aborts the pending loads of the first, with a generation counter checked between every slot step. Profile switching under pressure is exactly when you hammer the switch button, and a queue would turn that into a10-second pileup of stale activations.

## Measured, not estimated

The planner runs on estimates, and estimates lie. The first real measurement made this unavoidable: the header-derived estimate for the E4B at working context totaled 3238 MiB, and the card measured ~4.1 GiB after load — an ~850 MiB gap that is CUDA workspace and cuda-graph overhead, invisible in any GGUF header, sitting between "should fit" and "does fit." The margin covers that gap once, but if every admission decision eats 850 MiB of slack, the 6 GB card holds two models instead of three.

So the planner got a memory. After each load, the manager snapshots device memory before and after, attributes the delta to that slot, and persists it in `state.json` keyed by engine version and GGUF mtime — invalidated automatically when either changes, because a rebuilt binary or a re-downloaded quant invalidates the measurement honestly. Second activations fit precisely. The design split is worth stating because it's the part I'd defend in review: plan on estimates, correct with measurements. Estimates have to exist (you can't measure a model you haven't loaded, and the first activation of a profile has no history), but letting estimates persist as the permanent basis of admission means paying the 850 MiB doubt forever. Persisted measurement converts "about 4.1 GB, plus a margin, probably" into a number the scheduler can pack against, and it's the difference between a ladder that rarely degrades and one that degrades on every activation.

## Chunked prefill, and the bug that taught me what it costs

The other piece that makes concurrent serving work on a small card is chunked prefill: a long prompt decodes incrementally across bounded batches instead of reserving worst-case compute buffers. It's standard technique and it worked, until it interacted with a hybrid-recurrent model in a way that produced the best debugging story of the project.

A Qwen3.5-4B reasoning distill — the model that mattered for grounded RAG — failed deterministically on long prompts: 2–3 completion tokens, empty content, immediate EOS, at temperature 0, reproducibly, while short prompts worked. Stock `llama-server` on the same GGUF, same batching pattern, same 6 prefill calls, was fine. The investigation eliminated everything obvious in order: rendered prompts were byte-identical to llama-server's (verified against a jinja2 reference render, zero diff), the reasoning-split was correct, greedy determinism ruled out numerics, KV type ruled out fp8-vs-f16, and single-sequence mode passed while multi-sequence failed — which turned out to be its own separate root cause, hybrid-recurrent architectures corrupting under multi-sequence contexts, fixed with an architecture-name clamp on `n_seq_max`.

The real root cause was one line of intent in my scheduler's chunked-prefill loop. It requested output logits on the last token of *every* prefill chunk, so a prompt split over N decode calls marked N−1 mid-prompt positions as outputs. For a transformer that's wasteful and harmless. For a hybrid Gated Delta Net model, whose fused chunked kernels depend on output handling, it corrupts generation into immediate EOS. Stock llama-server requests output on the final prompt token only. The fix was to set `want_logits` only when the drained chunk empties the prefill queue — intermediate chunks decode with zero outputs, exactly like the reference implementation. Six decode calls went from 2 tokens of garbage to 243 tokens of correct, cited answer.

What this taught me is the actual price of chunked prefill: not the batching arithmetic, which is easy, but that splitting a decode across calls changes the semantics of every flag you set per call, and the models that punish the mistake are precisely the new architectures you adopted the model for. The table in the investigation doc — n_batch 4096 passes, 192 fails, llama-server at 192 passes — is my favorite artifact in the repo, because it's the shape of a real bug: one variable, one control, and the divergence is entirely in code you wrote yourself.

One more entry in the same genre, because it's the best argument for integration tests over unit tests: under `speculative = "auto"`, the engine paired the OCR model — a 129,280-vocab `deepseek2-ocr` arch — with the standard gemma4 drafter, whose 262,144-vocab tokens are invalid in the target's vocabulary. The out-of-vocab draft token crashed the target decode, the error propagated as `?` characters, and the slot *leaked into the next request* — OCR returned `X=17/Y=0` corruption on every subsequent call. The fix was a vocabulary-match gate on draft pairing, but the deeper fix was a rule: speculation is a correctness hazard, not an optimization, when the drafter's vocabulary isn't a subset of the target's. Both this and the logits bug were invisible to any test that didn't run the real GGUF on the real GPU, which is why the model-backed test files exist as `--ignored` harnesses run deliberately.

## One core, many dialects

The API surface is deliberately promiscuous: OpenAI `/v1/chat/completions` with per-token logprobs, Ollama `/api/*` with nanosecond timings and NDJSON streaming, Anthropic `/v1/messages` with its own SSE event grammar, Cohere-shaped `/v1/rerank`. The reason is not check-box completeness — it's that every downstream tool speaks one of these dialects, and a local engine's value is being drop-in for whatever the client already uses. The engine underneath is one; the dialects are thin mappers over a shared stream consumer, so hooks and accumulation logic exist exactly once.

The annoying part was not the routes; it was that each ecosystem's quirks are load-bearing for somebody. Ollama clients send extra fields, so request types deliberately don't `deny_unknown_fields`. Anthropic's reasoning models need `message.reasoning_content` separated from content, tag-wise, per chunk, with the end-of-stream remainder riding on the finish chunk's delta. OpenAI logprobs must be actual log-probabilities (an early version emitted raw probabilities — a downstream consumer's token-surprisal confidence system was eating the difference), must be present when requested on streaming paths per-chunk, and the hooks fire from the logprob trace even when the client didn't ask, because a hook that can't see token confidence is decoration. Gemma 4's jinja template breaking the C `llama_chat_apply_template` with -1 was the forcing function for owning prompt rendering, and once owned, it became the place reasoning-split guarantees live. None of this is architecturally interesting. All of it is why "OpenAI-compatible" is a claim you should test against real clients, not declare.

This surface discipline has a downstream consequence worth naming: mettle is the supported local engine behind [docket](https://github.com/adityam23/docket), a local RAG engine for long documents, which talks to it exclusively across the OpenAI-compatible `/v1` HTTP API and never imports its code. That contract — stable response shapes, logprobs when asked, structured degradation errors — is why mettle can be the engine for a product without being "finished." The `/engine/*` profile surface docket renders in its dashboard is capability-detected, so a plain llama-server backend degrades honestly to "unavailable" rather than lying.

## On publishing no numbers

The README publishes no benchmarks. Not because there aren't any — the migration spike produced a table worth framing — but because a tokens-per-second number for a local inference engine is a claim about someone else's GPU, someone else's quant, and someone else's prompt length, and every one of those variables dominates the engine's contribution. The honest artifact is `mettle bench`, which drives streaming chat on *your* card and emits TTFT and aggregate tokens/s as reproducible JSON. The refusal to print a leaderboard number is itself a position: the interesting question is never "how fast is this engine" but "how fast is this engine on the model and card you actually have," and only the user's harness answers that. I'd rather ship the harness and an opinion than a number that's wrong in your hands.

## What the card taught

The through-line, looking back, is that every hard problem in mettle was a resource-accounting problem wearing a different costume. The mistralrs era failed on VRAM accounting (KV for layers that never write cache, embeddings tables in the wrong place). The migration was justified by a throughput measurement and executed against a `!Send` boundary that forces one worker — a scheduling constraint imported from C. The profile manager exists because the card can hold three models but not three *naive* copies of three models. Measured footprints exist because an 850 MiB estimate error is the difference between coexistence and eviction. Even the two best bugs — logits-on-intermediate-chunks corrupting a hybrid-recurrent model, and a drafter's vocabulary crashing an OCR slot — were failures of accounting: marking positions as outputs that weren't, spending decode validity on tokens that weren't in budget.

The naive version of this project is "a wrapper around llama.cpp with nice APIs." The actual project is a small operating system for 6 GiB of HBM-adjacent memory: admission control with a margin, measured footprints persisted against invalidation keys, a degradation ladder with refusal at the bottom and events at every rung, and a scheduler that would rather say no in a structured way than say yes and die. The GPU was the easy part. Deciding what happens when it's full was the product.
